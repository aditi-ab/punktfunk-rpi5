Plugins extend the host through the **scripting runner** (see [Events & hooks](/docs/automation)). A
plugin runs alongside the host, reconciles titles into your [game library](/docs/game-library) as a
provider — so they appear in the grid on every client — and can add its own page to the
[web console](/docs/web-console).

**Your game library is built from plugins** — the host scans no launcher on its own; install the one
for each launcher you use.

| Plugin | Host | What it does |
|---|---|---|
| **Steam** | Linux, Windows | Installed Steam titles and non-Steam shortcuts, with Steam's own art, plus a Big Picture tile. |
| **Lutris** | Linux | Your Lutris games, with art, and a tile that opens Lutris itself. |
| **Heroic** | Linux | Everything Heroic manages — Epic, GOG and Amazon — plus a tile that opens Heroic. |
| **Epic Games Store** | Windows | Installed Epic titles, from the launcher's own manifests. |
| **GOG** | Windows | Installed GOG games, launched directly — Galaxy is never involved. |
| **Playnite** | Windows | Mirrors your [Playnite](https://playnite.link) library — every store and emulator it manages — launched back through Playnite. |
| **Ubisoft Connect** | Windows | Installed Ubisoft titles, launched back through Ubisoft Connect. |
| **Amazon Games** | Windows | Installed Amazon Games titles, launched back through Amazon Games. |
| **Battle.net** | Windows | Installed Blizzard titles, launched through Battle.net (must already be running). |
| **Desktop entries** | Linux | Every Game-category application menu entry, Flatpak included, that no other source lists. |
| **Bottles** | Linux | The programs you added to each Bottle, launched through `bottles-cli`. |
| **itch.io** | Linux, Windows | Games installed by the itch app, with covers, launched directly. |
| **ROM Manager** | Linux, Windows | Scans your ROM directories, matches each platform to an installed emulator, and syncs them into the library with box art. |
| **VirtualHere** | Linux, Windows | Hands a real USB device on the couch — wheel, HOTAS, pad — to the host while you play. Needs [VirtualHere](https://www.virtualhere.com/), sold separately. |

Amazon Games and the itch app keep their databases under your user profile, which the Windows
plugin runner can't read by default — each plugin's README carries the one-line `icacls` grant.

## Installing from the console

Every plugin runs inside the **plugin runner**, a separate service — installing while it's off
succeeds and starts nothing, so check it first:

1. **Plugins → Installed → Plugin runner** card. *Not installed*: install the runner package
   ([Troubleshooting](#troubleshooting)). *Disabled*: press **Enable runner** — once per host.
   *Stopped*: the runner is enabled but not up; its log says why.
2. **Browse** → pick a plugin → confirm. The host installs it, restarts the runner, and the
   plugin's page appears in the console's nav.

**Sources** is the third tab: where catalogs come from.

### What "Verified" means

Every catalogued plugin pins **one exact version** and its package hash. **Verified** means unom
reviewed *that exact package* — a new release keeps offering the reviewed version until the new one
is reviewed. Before downloading, the host re-checks the pinned hash against the registry, so a
package republished under the same version is refused.

A catalog can also **revoke** a version: the console shows the advisory and won't install it — or
warns on **Installed** if you already have it. It never removes running code for you.

| Badge | Where it came from |
|---|---|
| **Verified** | The built-in catalog. unom reviewed this exact package. |
| **External source**, *from &lt;source&gt;* | A catalog **you** added. Still pinned and hash-checked, but curated by somebody else. |
| **Unverified** | Installed by hand from a package spec. Nothing pins it; the console asks you to type the name to confirm. |

### Adding another catalog

**Sources** → *Add a catalog source*: a name and the URL of its index. Optionally paste the source's
`ed25519:…` public key — with a key set, the host refuses any unsigned index from that source.
Adding a source is a one-time trust decision: its plugins become installable, always attributed to
it, never **Verified**.

To publish to the built-in catalog, open a pull request against
[`punktfunk-plugin-index`](https://git.unom.io/unom/punktfunk-plugin-index).

## Installing from the CLI

<Tabs items={['Linux', 'Windows']}>
<Tab value="Linux">

```sh
punktfunk-host plugins add playnite     # or: rom-manager
punktfunk-host plugins enable           # turn the runner on (once)
```

On **SteamOS** the [host installer](/docs/steamos-host) ships the runner automatically.

</Tab>
<Tab value="Windows">

Run from an **elevated** PowerShell — the plugins directory is under admin-owned
`%ProgramData%\punktfunk`. The runner task runs as the low-privilege `NT AUTHORITY\LocalService`
account; `plugins enable` sets that up.

```powershell
punktfunk-host plugins add playnite     # or: rom-manager
punktfunk-host plugins enable           # turn the runner on (once)
```

If `punktfunk-host` isn't found, open a **new** terminal, or use the full path:
`& "$env:ProgramFiles\punktfunk\punktfunk-host.exe" plugins add playnite`.

</Tab>
</Tabs>

The plugin's page then appears in the [web console](/docs/web-console)'s nav automatically.

The runner is **on by default** on a new install. It discovers plugins at start, so one installed
later needs a runner restart — `systemctl --user restart punktfunk-scripting` on Linux,
`Restart` the `PunktfunkScripting` task on Windows; the console does that restart as part of
installing.

Don't want it? `systemctl --user mask punktfunk-scripting` on Linux, or disable the
`PunktfunkScripting` scheduled task on Windows. The host keeps streaming; you lose plugin-provided
game sources and automation.

A plugin installed from the CLI shows in the console as **Installed via CLI** — install the same
plugin from **Browse** and it carries its catalog badge instead.

### The rest of the commands

| Command | What it does |
|---|---|
| `punktfunk-host plugins add <name…>` | Install one or more plugins. |
| `punktfunk-host plugins remove <name…>` | Uninstall. |
| `punktfunk-host plugins list` | List what's installed, with versions. |
| `punktfunk-host plugins enable` | Enable + start the runner. |
| `punktfunk-host plugins disable` | Stop + disable the runner. |
| `punktfunk-host plugins status` | Is the runner enabled and running? |
| `punktfunk-host plugins grant <plugin> <dir> [--write]` | Allow a folder directly; read-only unless `--write`. |
| `punktfunk-host plugins access` | List grants, pending requests and denials. |
| `punktfunk-host plugins revoke <plugin> <dir>` | Remove one grant. |

A bare name resolves to the first-party package — `playnite` installs `@punktfunk/plugin-playnite`
from Punktfunk's own registry. Any other name installs from the **public npm registry** and is
refused unless you add `--allow-public-registry` — a guard against typos and look-alike packages.

## Where a plugin runs

On Linux each plugin runs in its own sandbox — a separate process with an empty home, no network
unless it asked for one, and access to just the paths it declared (plus what you granted it). It
reaches the host through a socket the runner holds, with a token of its own, so it can publish its
own library entries and nothing else's. The sandbox is built from the `punktfunk` block in the
plugin's `package.json` (below), so a plugin without one does not start; update it.

That needs **bubblewrap** (`bwrap`), which the packages depend on. If a host cannot build a sandbox
— no bwrap, or a kernel with unprivileged user namespaces switched off — no plugin runs at all, and
Troubleshooting says which of the two it is. `PUNKTFUNK_PLUGIN_SANDBOX=off` in `host.env` runs them
in the runner's own process instead: that is your whole account, and the console says so while it
is set.

On **Windows** the runner is a low-privilege account (`NT AUTHORITY\LocalService`) rather than a
sandbox, and plugins share it.

Scripts you drop in `~/.config/punktfunk/scripts/` are your own code and are not sandboxed — the
same as anything else you run yourself.

> Plugins are operator-installed code. Install only plugins you trust, from a registry you control.

## What a plugin may run

A plugin never hands the host a command line. Each package declares, in its own `package.json`, the
paths it reads and the **programs** the host may run for it — the program and the shape of its
arguments, with a placeholder for each value:

```jsonc
"punktfunk": {
  "schema": 1,
  "id": "rom-manager",
  "reads": ["~/.var/app/org.libretro.RetroArch"],
  "exec": {
    "retroarch": {
      "exe": "retroarch",
      "args": ["-f", "-L", "{core}", "{rom}"],
      "params": { "core": "id", "rom": "path" }
    }
  }
}
```

A library entry then names the template and supplies the values. The host checks each against the
character class the template declares, refuses a path outside the directories that plugin may
reach, and builds the argv itself — so a value is always one argument, never syntax. That
declaration ships inside the reviewed, hash-pinned tarball; nothing the plugin says while running
can widen it.

**Your own directories.** A package cannot know where you keep ROMs or games. When its scanner
finds a folder it cannot read, the Library source shows the exact path and whether it asks for read
or write access. Choose **Allow** or **Don't allow** there. Allowing it restarts only that plugin;
read access is the default.

The Installed plugin row lists every grant and denial. Remove a grant there, or choose **Ask again**
to clear a denial. The CLI is the alternative:

```sh
punktfunk-host plugins grant rom-manager /mnt/games/roms
punktfunk-host plugins access
punktfunk-host plugins revoke rom-manager /mnt/games/roms
```

Use `--write` only when the plugin must change files in that folder. A request is only a suggestion:
nothing reaches the sandbox until you allow it.

## Windows: a plugin that says "not installed"

The runner is a de-privileged account (`NT AUTHORITY\LocalService`), so it can't read anything
inside **your** user profile — a launcher or database under `%AppData%` or `%LocalAppData%` is
invisible to it and reads exactly like one that isn't installed.

When a plugin finds that launcher path, it asks through the same Library source row. Allowing it
adds read-only access to that folder and everything under it; the rest of your profile stays
closed. The CLI command above remains available from an elevated PowerShell.

## Updating and removing a plugin

**Update.** The **Installed** tab grows an **Update to &lt;version&gt;** button whenever the catalog
pins a newer version; it installs and restarts the runner. From a terminal, re-run
`punktfunk-host plugins add <name>` — it installs the newest version the *registry* has (not the
catalog pin) and does **not** restart the runner: restart it yourself.

**Remove.** The **Uninstall** button removes the package *and* restarts the runner.
`punktfunk-host plugins remove <name>` removes the package only — restart the runner to stop a
plugin still running.

A plugin's config and cache stay —
`~/.config/punktfunk/plugin-state/<plugin>/` on Linux,
`%ProgramData%\punktfunk\plugin-state\<plugin>\` on Windows — so re-installing picks your settings
back up.

To stop *every* plugin without uninstalling: **Disable runner** on the Installed tab, or
`punktfunk-host plugins disable`.

## ROM Manager

`@punktfunk/plugin-rom-manager` — point it at your ROM directories and it scans them, matches each
platform to an installed emulator, fetches box art (SteamGridDB, or the keyless libretro
thumbnails), and reconciles the result into your library. ~25 built-in platforms, per-game
overrides, and a console page to configure it all.

```sh
punktfunk-host plugins add rom-manager
```

Then add a root or two — from the console's **ROM Manager** page, or in the config file:

<Tabs items={['Linux', 'Windows']}>
<Tab value="Linux">

`~/.config/punktfunk/plugin-state/rom-manager/config.json`:

```jsonc
{
  "roots": [
    { "dir": "/mnt/roms/snes", "platform": "snes" },
    { "dir": "/mnt/roms/ps1", "platform": "ps1", "excludes": ["*.sav"] }
  ],
  "art": { "provider": "auto", "steamGridDbKey": "" }
}
```

</Tab>
<Tab value="Windows">

`%ProgramData%\punktfunk\plugin-state\rom-manager\config.json`:

```jsonc
{
  "roots": [
    { "dir": "D:\\roms\\snes", "platform": "snes" },
    { "dir": "D:\\roms\\ps1", "platform": "ps1", "excludes": ["*.sav"] }
  ],
  "art": { "provider": "auto", "steamGridDbKey": "" }
}
```

</Tab>
</Tabs>

`plugin-state` is where a plugin reads and writes its own files — on Windows it's the one
directory `plugins enable` grants the low-privilege runner write access to; a config file placed
anywhere else under `%ProgramData%\punktfunk` is not read.

Full options and the platform/emulator list:
[the plugin's repo](https://git.unom.io/unom/punktfunk-plugin-rom-manager).

## Playnite

`@punktfunk/plugin-playnite` — mirrors your **[Playnite](https://playnite.link)** library into
yours; launching a title hands it back to Playnite, and covers are served by the host.

Playnite keeps its library locked while running, so there are **two parts**, both on the **Windows
host**:

1. **The plugin** — from an elevated PowerShell:

   ```powershell
   punktfunk-host plugins add playnite
   punktfunk-host plugins enable
   ```

2. **The Punktfunk Sync extension** (in Playnite) — download `punktfunk-sync.pext` from the
   [plugin's builds](https://git.unom.io/unom/punktfunk-plugin-playnite/actions), **double-click**
   to install it like any add-on, restart Playnite once.

The console's **Playnite** page shows "Exporter connected", and games sync within seconds of any
library change. Filters live on that page or in
`%ProgramData%\punktfunk\plugin-state\playnite\config.json`. Details:
[the plugin's repo](https://git.unom.io/unom/punktfunk-plugin-playnite).

## VirtualHere (USB passthrough)

`@punktfunk/plugin-virtualhere` — hands a **physical USB device** on your couch machine to the host
while you play: the game sees the real device — the answer for a racing wheel, HOTAS, pedals or
arcade stick.

<Callout type="warn">
This plugin drives [VirtualHere](https://www.virtualhere.com/), a commercial USB-over-IP product
**sold separately** by VirtualHere Pty. Ltd. Nothing from VirtualHere is bundled or downloaded by
Punktfunk — you install and license it yourself. The plugin is not affiliated with or endorsed by
VirtualHere.
</Callout>

You need both halves of VirtualHere running first:

- **The USB Server on the couch**, sharing the device. Free for one device; beyond that, and to run
  the client as a service, VirtualHere requires a purchased licence.
- **The USB Client on the host**, ideally installed as a service so it survives logging out.

Servers exist for Windows, Linux, macOS and Android couches. **There is no VirtualHere server for
iOS or tvOS.**

```sh
punktfunk-host plugins add virtualhere
punktfunk-host plugins enable
```

The console's **VirtualHere → Devices** page lists whatever the couch is sharing; pick one and it
writes a rule matching the device *by name*, which survives reboots and port changes. By default the
device is handed over when video starts and returned when it stops; you can widen that to the whole
session, or to the entire time a client is connected.

If nothing happens, the **Diagnostics** tab walks the two-sided setup and names the part to fix —
the same checks as `punktfunk-plugin-virtualhere doctor`. Full configuration:
[the plugin's repo](https://git.unom.io/unom/punktfunk-plugin-virtualhere).

## Troubleshooting

**`punktfunk-host: command not found`** — on Windows, open a new terminal so it picks up the
installer's `PATH` change, or call the exe by full path. On Linux the package installs it to
`/usr/bin/punktfunk-host`.

**"the plugin runner isn't installed"** — the runner is its own package: `sudo apt install
punktfunk-scripting` (Ubuntu), `sudo dnf install punktfunk-scripting` (Fedora, from the
[same RPM repo](/docs/fedora)), `sudo pacman -Syu punktfunk-scripting` (Arch — a full `-Syu`),
re-run `scripts/steamdeck/install.sh` (SteamOS), `services.punktfunk.scripting.enable` (NixOS, on
whenever the host is), re-run the installer keeping the scripting component (Windows).

If the runner *is* installed and the host still says it isn't, the host can't find the
`punktfunk-scripting` executable — it looks beside its own binary, then on `PATH`, then in the
packaged `/usr` and `~/.local` layouts. Point `PUNKTFUNK_SCRIPTING` at it (see
[Configuration](/docs/configuration)). The console installs plugins from inside the host *service*,
whose `PATH` is much shorter than your shell's — a runner that `plugins add` finds and the console
doesn't is that difference, and the env var is the fix.

**A plugin can't read one of its folders** — open its Library source. A valid request appears with
the exact path; allow it there. Missing drives and protected paths are refused by the host and
never appear. The host's admin token and identity key stay out of reach either way — see
[Security](/docs/security).

**A plugin's interface won't load** — see
[Connection & discovery](/docs/troubleshooting-connect#a-plugins-interface-doesnt-load): plugin UIs
are served on **TCP 47993**, so the port has to be open *and* its certificate accepted.

**Where a plugin's log output goes** — the console's **Troubleshooting** page, isolated by the
**Sources** chips, tagged `plugin:<name>` (`plugin:runner` for the supervisor). An empty Plugins view almost always
means the runner isn't running — check with `punktfunk-host plugins status`.

<Callout>
Nothing is lost if the host is down: the runner keeps buffering and sends the backlog when the host
comes back.
</Callout>

**Reading the runner's log directly** — the ground truth if the runner can't reach the host:

<Tabs items={['Linux', 'Windows']}>
<Tab value="Linux">

```sh
journalctl --user -u punktfunk-scripting -f
```

</Tab>
<Tab value="Windows">

The runner task writes `%ProgramData%\punktfunk\plugin-state\runner.log` (previous run:
`runner.log.1`).

```powershell
Get-Content "$env:ProgramData\punktfunk\plugin-state\runner.log" -Tail 100
```

If the file doesn't exist, the task started before `punktfunk-host plugins enable` ever ran (which
makes `plugin-state` writable for `LocalService`) — run it from an elevated prompt. To watch a
start live:

```powershell
& "$env:ProgramFiles\punktfunk\bun\bun.exe" "$env:ProgramFiles\punktfunk\scripting\runner-cli.js"
```

</Tab>
</Tabs>

**A plugin can't reach a service running on the same box (Linux)** — plugins that drive a local
daemon talk to it over a socket or FIFO in `/tmp`. A runner unit with `PrivateTmp=yes` (earlier
releases, or a drop-in that reinstates it) hides the real `/tmp`: the plugin launches the vendor's
binary and times out reaching the daemon. Fix:

```sh
systemctl --user edit punktfunk-scripting
```
```ini
[Service]
PrivateTmp=no
ReadWritePaths=/tmp
```

## Writing your own

A plugin is a TypeScript module built on **`@punktfunk/plugin-kit`** (`definePluginKit`), supervised
by the runner. The kit owns lifecycle, config and state, the library sync engine, and serving the
plugin's console page. Start from the
[plugin-kit README](https://git.unom.io/unom/punktfunk/src/branch/main/plugin-kit) and
[ROM Manager](https://git.unom.io/unom/punktfunk-plugin-rom-manager), the reference implementation.

A library plugin declares folders discovered from launcher data with `wants`. The kit checks them
before every scan, batches unusable paths into one request, and scans whatever is reachable now:

```ts
export default defineLibraryPlugin({
  // …name, schema, detect and scan…
  wants: (config) => launcherLibraryFolders(config),
})
```

Inside the Linux sandbox an unbound directory and a missing drive both look like `ENOENT`, so the
kit asks for `missing` paths there and lets the host check the real filesystem. Outside the sandbox,
only permission-denied paths are requested. The same unreachable set is posted once per run; a
grant restarts the plugin and starts a fresh scan.

Plugins that do not use `defineLibraryPlugin` can yield `requestAccess(paths, reason)` from
`@punktfunk/plugin-kit`. It only creates pending rows. Never tell users to widen the runner unit or
change ACLs by hand; the operator's Allow action is the grant.
